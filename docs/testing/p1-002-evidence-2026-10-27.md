# P1-002 evidence — 27 October 2026

Status: **blocked**. Target: local `DSM-7.4-Test` Arc Loader VM. PHP is rejected as a request runtime and the standalone Go/FastCGI prototype cannot derive the DSM session identity through the documented `authenticate.cgi` route. Package lifecycle and upgrade were observed; authenticated routing remains blocked.

On 27 October 2026, Package Center first rejected the locally packed SPK as an invalid file format. The outer archive was compressed and package icons were absent. The build now creates an uncompressed outer tar archive, required 64×64 and 256×256 PNG icons, and an MD5 for `package.tgz`, matching the published DSM package layout. Package Center then accepted the archive format but rejected its privilege declaration as root. The privilege metadata was reduced to the documented minimal `run-as: package` form; Package Center then installed the package and created the `mediainfo-poc` account (UID/GID 241653).

Live root diagnostics showed that DSM generated an active `pkgctl-mediainfo-poc.service` and loaded the nginx route, while the runtime remained under the `mediainfo-poc` account. Nginx workers run as `http:http`; their connection to the `0660 mediainfo-poc:mediainfo-poc` socket returned 502. Temporarily changing only that socket group to `http` yielded the runtime's expected unauthenticated 401 response, proving the request path and fail-closed authentication behavior. DSM rejected the one-shot root `postinst` approach in 0.1.0-0006 as root privileges. Version `0.1.0-0008` retains the package-owned process and uses only a local Unix socket with mode `0666`, avoiding a root script and any TCP listener; every FastCGI request still invokes DSM authentication before returning data. A root `synopkg install` diagnostic revealed error 261: an upgrade requires both `preupgrade` and `postupgrade` scripts. The package now contains explicit no-op hooks for that DSM requirement.

The 0.1.0-0008 upgrade passed Package Center validation. An authenticated browser route request still returned the controlled 401 response; 0.1.0-0009 added basic CGI gateway, request-method, script-name, and DSM-server-address variables but did not change that result. Version 0.1.0-0010 forwards the remaining request-derived custom-CGI context required by the documented route: host, port, protocol, request URI, and query string. It still passes no caller-controlled identity header and never records session material.

PHP gate observation: on the tested VM, `/bin/php` is PHP 8.1.32 CLI (built 20 June 2025), visible unchanged to `mediainfo-poc`; it exposes `bcmath`, `bz2`, `curl`, `ldap`, `mbstring`, `openssl`, `PDO`, `pdo_sqlite`, `sqlite3`, `xml`, and the other modules recorded in the root-shell transcript. No `php-cgi` executable, installed PHP package, or Web Station package exists. Synology documents Web Service as a Web Station provider, not a standalone SPK request contract. CLI PHP and its development server are not acceptable HTTP handlers. PHP therefore fails the dependency-free package request-route and documented-support gates.

## Decision

PHP is **rejected** for this package: the observed CLI binary is not a documented, package-owned HTTP request path and Web Station is absent. The static Go runtime, lifecycle, Web Config registration, and package-account execution are proven, but its authenticated FastCGI route remains **rejected**: an authenticated DSM browser request returns 401 after the documented CGI context is forwarded to `authenticate.cgi`. P1-002 is therefore **blocked**. Do not weaken authentication, trust a browser-supplied identity, add a root broker, or add Web Station merely to pass this gate. A future route may resume P1-002 only with a documented standalone DSM package mechanism that preserves authenticated request identity.
